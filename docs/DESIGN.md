# Crosscheck — Design v0.1

Status: draft, 2026-07-24. Synthesized from three independent architecture passes (adoption-first, protocol-first, capture-quality-first) and two adversarial reviews. See [RESEARCH.md](RESEARCH.md) for the evidence behind every verdict referenced here.

## 1. Problem and wedge

Developers on the same team each run their own coding agent. Most work happens locally — uncommitted, unpushed, often unfinished — so neither teammates nor their agents know what is being investigated, planned, or changed in parallel. Git surfaces overlap only at merge time, only at file granularity. The expensive collisions are semantic: two people debugging the same symptom with different root-cause theories, contradictory fixes in different files, duplicated investigation.

The prior-art sweep (RESEARCH.md §1) shows the landscape splits into five clusters — file-collision coordinators, team-memory layers, session sharers, git-synced work graphs, single-user orchestrators — and **nobody occupies the intersection we target**:

1. A **living diagnosis graph**: observation → hypotheses (with status) → evidence → root-cause chain → rejected approaches, which agents of *different* developers can extend and contradict rather than overwrite.
2. **Semantic matching of in-flight work** across different vocabulary ("login 500s" ≈ "JWT validation regression").
3. **Proactive injection** of a teammate's relevant findings into a live session (hook-driven push, not inbox-checking).
4. **Diagnostic conflict surfacing**: two open, contradictory root-cause theories for the same symptom.

Positioning: *"GitHub sees the past; crosscheck sees the present."* We are explicitly **not** another team-memory MCP (commoditized, 0–30-star graveyard), not an orchestrator for one developer's agents, and not a session-transcript sharer.

## 2. Architecture

Hub-and-spoke. No peer-to-peer agent messaging (wrong topology per protocol research). One TypeScript monorepo.

```
 Dev A machine                                Dev B machine
┌───────────────────────────┐               ┌─────────────────────┐
│ Claude Code               │               │ Claude Code         │
│ ├ hooks: capture + inject │               │ ├ hooks             │
│ ├ MCP tools (diagnosis)   │               │ ├ MCP tools         │
│ ├ statusline: presence    │               │ └ statusline        │
│ └ spool ~/.crosscheck/    │               │                     │
└──────────┬────────────────┘               └─────────┬───────────┘
      HTTPS + SSE (Last-Event-Id cursor)         HTTPS + SSE
           └───────────────┬──────────────────────────┘
                 ┌─────────▼──────────────────────┐
                 │ `npx crosscheck-hub serve`     │
                 │ Hono API · SSE · outbox events │
                 │ PGlite+pgvector │ or Postgres  │
                 │ presence · claims · hybrid RRF │
                 └────────────────────────────────┘
```

Key shell decisions (adoption-first pass, confirmed by both judges):

- **Server**: single process, `npx crosscheck-hub serve`, with **PGlite + pgvector embedded** — no Docker, no DB install. `DATABASE_URL` flips the same Drizzle code to real Postgres for larger teams. One Postgres dialect, two runtimes. *Open validation item: PGlite is single-connection WASM — load-test concurrent ingest + SSE + vector search before v0 ships; if it can't hold the hook latency budget, docker-compose Postgres becomes the default and PGlite the solo-trial mode.*
- **No local daemon.** The connector is hook scripts + an MCP server — short-lived processes only. Offline writes spool to `~/.crosscheck/` and flush on the next hook invocation.
- **Realtime**: SSE with `Last-Event-Id` cursor over an **events outbox table** (durable replay; NOTIFY/in-process emitter is only a latency optimization). No Redis, no WebSockets, no queues.
- **Auth**: per-developer API keys (provenance is a core feature; shared team tokens destroy attribution and revocability). TLS via reverse proxy or Tailscale — documented, not built.
- **Install** = one PR: `crosscheck init` writes `.claude/settings.json` (hooks, statusline) + `.mcp.json` (project scope) into the team repo. Every teammate is connected on next `git pull` + one `crosscheck login <url>`.
- **Summarizer auth**: reuses the developer's existing Claude Code auth via headless `claude -p` (Haiku-class). No new API key — a silent adoption killer removed.

### 2.1 Scoping & trust boundaries

Who can talk to whom is decided by infrastructure, not by a toggle someone can misconfigure:

- **Agents never talk to each other directly.** Everything flows through a hub. There is no global agent network and deliberately no "talk to anyone" mode — that would be the trust disaster this section exists to prevent.
- **One hub = one trust space.** A hub is started per project or group (`npx crosscheck-hub serve` on any teammate's machine + Tailscale, or a small VPS). Company affiliation is irrelevant: a "team" is exactly the set of people holding keys to a hub. A developer can be in any number of hubs (work team, side project with a friend) — those spaces are separate infrastructure and know nothing of each other.
- **The repo decides where a session reports.** The connector is enabled per repository: `crosscheck init` writes the hub URL into the repo's committed config. A session in the work monorepo talks to the work hub, a session in the side-project repo talks to the side-project hub, a session in any unconnected directory talks to nobody. When a session's cwd resolves to no reportable repo (an editor workspace rooted at the repo's PARENT folder — a real trial incident), the connector derives the repo from the TOUCHED FILE's path instead: an upward walk to the file's own innermost repo, which reports only if ITS root carries the committed config. The cwd path holds the same line since the user-level install landed (finding #11): hooks wired once at the user scope fire in every directory on the machine, so a merely logged-in developer's stored hub URL no longer stands in for a missing committed config on any reporting surface — only the repo's own `.crosscheck.json` (or an explicit `CROSSCHECK_HUB_URL`, an operator's per-process instruction) makes a repo reportable (`loadReportableConfig`, pinned both directions by `packages/connector-claude/test/global-wiring-silence.test.ts`). The walk stops at the first repo boundary, so an unconnected repo nested inside a connected one stays silent, and a session that touches only unconnected files stays invisible forever (pinned by `packages/connector-claude/test/e2e/parent-workspace.e2e.test.ts` and `packages/connector-core/test/connected-repo.test.ts`). Nothing runs 24/7 on the developer's machine — hooks only execute while a session is active; only the hub is long-running.
- **People join by invitation only.** Per-developer API keys (`crosscheck invite` on the hub, one-time `crosscheck login <hub-url> <key>` per developer), individually revocable.
- **Within a hub, sharing has defaults and gates:** only structured claims, file paths, and hashed error fingerprints by default — never raw transcripts or full diffs; artifacts default to `needs_approval` (owner-only until released); per-developer presence opt-out and `mute`; local secret-scan before every upload. v0 exposes these controls via CLI, v0.5 adds the web UI (feed, member list, click-to-approve). Work contexts, claims, and claim edges are team-visible to every authenticated hub member by design — cross-developer read inside a hub is the product (see the extend_diagnosis flow); only artifacts carry per-item sensitivity gates.
- **Presence opt-out and mute are hub-enforced, with a hard scope line.** `crosscheck presence off` hides a developer's LIVE presence from every surface other developers see — presence list (briefing "active teammates", statusline), PreToolUse tripwire, absence "inactive" findings (absence reporting is presence surveillance too), and every activity-feed event attributed to them on `/api/events`(+`/stream`) — knowledge kinds included, because feed rows carry server timestamps and `work_context_created` fires at the start of a piece of work, making a kind-scoped filter a presence bypass — inside each query's WHERE on the hub, so a modified connector cannot see them either; their own view of themselves is unaffected. It does NOT retract published knowledge: claims, diagnoses and solved trees stay visible and attributed on every pull surface (hiding an event row hides its timing from the feed, never the knowledge itself) — the control covers the surveillance surface, not authorship, and the CLI says so when opting out, including the one loophole it cannot close: commits under a git email the hub cannot match still surface as "unconnected" absence lines. `crosscheck mute <developer>` is the reader-side mirror: it suppresses that developer's content from the READER's unasked surfaces only (prompt hints, briefing pointers, presence displays, tripwire asks) and is stored hub-side per reader so it follows them across machines; muted content stays reachable by deliberate pull (`search_related_work`, `get_diagnosis`, `get_referee_brief`) — mute is a preference, never a boundary. Suppressed hints are never recorded in `hint_deliveries` (they were not delivered). The authoritative surface list lives in `packages/server/src/services/visibility.ts`; pinned by `packages/server/test/presence-optout.test.ts` and `test/mute.test.ts`, which read the raw API as another developer.
- **Reads are hub-scoped, not repo-scoped — including the MCP tools.** This is the same rule as the bullet above, stated on the axis people actually ask about, because "one hub = one trust space" and "the repo decides where a session reports" together imply it without saying it, and an unstated implication is how a boundary gets invented by accident. A member of a hub may read and extend **any** work context in it, whatever repo the session that created it was in: `get_diagnosis` and `extend_diagnosis` take an id and do not consider the caller's repo. `search_related_work` *is* repo-scoped, and that is a **relevance filter, not a boundary** — it answers "what is being worked on here", and the id it withholds is still readable by id. It could not be a boundary even if it were meant as one: the repo is derived from the git remote on the caller's own machine, and the hub cannot re-derive it from an API key, because one developer legitimately works across many repos against one hub. Enforcement would have to move to the hub *and* the product would have to want it — and it does not: a claim about an API contract published from `acme/api` is exactly what somebody in `acme/web` needs. Pinned by `packages/connector-core/test/mcp-repo-scope.test.ts`, which drives two repos against one hub, so a future round cannot flip this axis in either direction without a test going red.
- **Addressed communication is not presence, and mute is not a wall.** The asynchronous question channel (roadmap R2) crosses both controls, so the line is stated rather than inferred. **Presence opt-out does NOT stop questions**: it hides a developer's LIVE presence — where they are, what they are running, when they last ran it — and a question addressed to a person by name is none of those things. An opted-out developer receives questions exactly as anybody else does, and the ASKER learns nothing about their presence through it: `ask_teammate` answers identically whether the target is live, idle or opted out, and never says whether anyone is there. **Mute DOES suppress a question from the reader's briefing**, because the briefing is an unasked surface and that is precisely what mute covers; the question is still stored and still listed by `list_open_questions`, which is a deliberate pull, exactly as a muted teammate's tree stays readable through `get_diagnosis`. Mute stays a preference, never a boundary, and it is never disclosed to the asker — their question simply expires, and `crosscheck doctor` tells THEM it expired without saying why. Enforced hub-side in the same `services/visibility.ts` conditions as every other surface.
- **What travels between repos is decided by IDENTITY, not by scope** (VISION.md §1 collective memory). The bullet above says reads are hub-scoped; this one says which MATCHES a hub is willing to make across that scope, because "a member may read any tree" and "the hub may assert that an old tree is relevant here" are different permissions. An **error fingerprint** is derived from the failure TEXT, so it means the same thing in every checkout and a solved tree carrying one matches current work on ANY repo of the hub — the line names the repo it came from so the reader is never left to assume it is local. A **file target** is a repo-RELATIVE path: `src/index.ts` names a different file in every repo, so it is identity only inside one, and a cross-repo path match is the fuzzy similarity that turns "you have seen this before" into noise. The **session-intent** tier is text overlap rather than identity and stays same-repo for a second reason too: the searchable document still folds in the repo label and the default branch name (audit row M13), so until that is cleaned up, prose matching across repos would make "rebase onto main" a hit on every repo the hub holds. `packages/server/src/services/solved-matches.ts` states the rule at `CROSS_REPO_TARGET_KIND` and `packages/server/test/solved-cross-repo.test.ts` pins both halves in one test.
- **Later, not v0: per-repo ACLs within one hub.** Until then the rule is simple: different trust requirements → different hubs. That is the escape hatch for anyone who wants the bullet above to be false: it is a second hub, not a setting.

## 3. Capture pipeline (knowledge OUT)

Three-tier trust ladder (capture-first pass — "tier = trust"):

**Tier 0 — deterministic signals.** Zero LLM, zero tokens:
- `SessionStart` hook → register session: repo (by remote URL, not path), branch, base commit, developer, agent kind. Fails open in 400 ms.
- `PostToolUse` (async) on Edit/Write → record file targets; symbols via a cheap tree-sitter pass. Doubles as heartbeat.
- `PostToolUse` on Bash → failing output becomes an **error fingerprint** (stack trace with line numbers/UUIDs/paths stripped, SHA-256). Highest-precision cross-session match signal, costs nothing.

**Tier 1 — draft claims (v0.5).** A **gated** Stop-hook summarizer: fires only when the turn matches diagnosis-moment heuristics (test ran, error output, hypothesis language) or — since trial finding #12, where a full day of reviews, fixes and merges produced zero claims — conclusion-moment heuristics (a verdict or decision declared, an approach ruled out, a review finding in review shape, a suite flipping red→green, a commit/merge boundary; every trigger a named predicate pinned by the conclusion corpus in `packages/connector-claude/test/fixtures/conclusion-corpus/`), debounced ≥2 turns apart, capped at 6/session. Headless `claude -p` over the turn's transcript slice emits schema-validated claim JSON or `NONE`. That nested claude is a model call and not a session (trial finding #14): it runs with the developer's whole login environment minus the parent session's markers, with no settings, hooks, MCP servers, tools or transcript persistence (`--setting-sources "" --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence --tools "" --max-turns 1`), from a neutral directory, and carries `CROSSCHECK_SUMMARIZER_CHILD=1`, under which every crosscheck hook entry returns silence — so it can neither register phantom sessions nor fire the summarizer recursively. Drafts get `capture_mode='auto'`, `provenance='derived'`, **confidence hard-capped at 0.5**, and are **never proactively injected** to teammates — only surfaced as pull-able pointers. A promotion loop (SessionStart reminds the agent of its own unreviewed drafts → confirm/edit/discard) turns passive capture into agent-verified knowledge without developer effort.

**Tier 2 — published claims.** MCP tools, the authoritative record (`provenance='declared'`):
`publish_claim`, `set_intent` (one sentence of what this session is trying to accomplish, on the caller's own work context — the only way an intent reaches confidence 1; a declared intent replaces a derived one, is never overwritten by a late derived record, and re-declaring supersedes; the sentence is secret-scanned before it leaves the machine — drop, never redact — because an intent is PUSHED into every teammate's briefing unasked, unlike a claim body, which stays a pointer until somebody pulls it), `extend_diagnosis` (add a claim + typed edge to *someone else's* tree — "your root cause is my symptom" = new claim + `deeper_cause_of` edge), `search_related_work`, `get_diagnosis` (full tree as markdown), `ask_teammate`/`answer_question`/`list_open_questions` (the asynchronous question channel — a question is secret-scanned before it leaves the machine for the same reason a declared intent is: both are PUSHED into a teammate's briefing unasked, unlike a claim body, which stays a pointer until somebody pulls it; an ANSWER is an ordinary declared claim on the answerer's own context plus an `answers` edge), `share_artifact` (sensitivity-gated). MCP invocation is unreliable on its own, so hook-injected reminders nudge at diagnosis moments.

**Session intent (trial findings #15/#16).** A work context carries `intent {summary ≤ 200 chars, provenance declared|derived, confidence, capturedAt}` beside its title. Titles are honest but thin — `feat/auth @ api`, or for a detached worktree the branch whose tip the commit sits on, else `detached@<sha> · <commit subject> @ repo` (the subject PROSE-sanitized and bounded at session start, two bounded git calls, never per tool). The intent says WHAT: on the first substantive prompt of a Claude Code session (≥ 40 chars, not a slash command, not a bare yes/no) the UserPromptSubmit hook books one fire under the state lock and spawns the summarizer's detached worker shape with a different prompt ("one sentence, ≤ 160 chars, third person, what this session is trying to accomplish, or NONE"); the worker writes a work_context UPDATE record (`provenance='derived'`, confidence fixed at 0.4 under the 0.5 derived cap the schema enforces) to the spool. The raw prompt never leaves the machine — 0600 file → model stdin → unlinked; only the model's sentence does, and only after the secret scan (drop, never redact), the echo-loop exclusion (a delivered teammate hint must not come back as this session's intent) and the wire contract. One fire per session state; the hub MERGES intents (a later work_context record without one keeps the stored intent; derived never overwrites declared). Cursor and ACP sessions get declared intents over MCP only (no `claude -p` there), like Tier 1.

**Ghost checks (VISION.md §3), two halves with different prices.** The DETERMINISTIC half is always on and costs no tokens: `GET /api/ghost-checks` intersects the caller's own live work contexts with their teammates' on the same repo — LIVE meaning unfinished and not merely recent, so a session with `ended_at` set and a work context with `landed_at` set are both excluded on both sides, and `GHOST_ACTIVE_WINDOW_DAYS` = 7 only decides how far back unfinished work still counts — and reports an overlap when they share one error fingerprint (content identity), `GHOST_MIN_SHARED_TARGETS` = 2 files/symbols, or `GHOST_INTENT_MIN_TOKEN_HITS` = 3 distinct words of the CALLER'S OWN intent. Precision is two exclusions borrowed from ConE (Maddila, Nagappan, Bird, Gousios & van Deursen, TOSEM 31(2), 2021 — 775 notifications over 26 000 pull requests on 234 Microsoft repositories, 554 of them rated useful): a value shared by more than `GHOST_HOT_TARGET_MAX_CONTEXTS` = 20 contexts on this repo is a lockfile and is dropped — counting only contexts that could appear in this reader's answer, so self-exclusion, presence opt-out and mute are in the WHERE of the rarity pre-filter exactly as they are in the two tiers, and an invisible developer's worktrees can never decide what the reader is shown, and a context carrying more than `GHOST_MAX_CONTEXT_TARGETS` = 50 values is a sweep and is dropped from BOTH sides of the SHARED-TARGET tier. The sweep rule stops there on purpose: it is an argument about sharing a file with somebody who shares files with everybody, and the intent tier shares no file — a sixty-file implementation session is ordinary work, so excluding it there would delete VISION §3's own flagship case, two plans that touch no common file and still collide. That tier keeps its own floor (`GHOST_INTENT_MIN_TOKEN_HITS`) and its own bound (`GHOST_MAX_INTENT_CANDIDATES`) instead. Those bounds are also what keeps the join from fanning out, and the honest statement of it is a PRODUCT rather than a claim about one value: the reader holds at most `GHOST_MAX_OWN_CONTEXTS` × `GHOST_MAX_CONTEXT_TARGETS` = 150 distinct values and every survivor of the hot rule has at most 20 sharers, so `GHOST_MAX_PAIR_ROWS` IS that product (3000) and the pair window cannot cut. It has to be arithmetic rather than a budget, because truncating that query would not shorten the answer but corrupt the count the floor is read off — a teammate whose two rows straddle the cut is judged below `GHOST_MIN_SHARED_TARGETS` and dropped whole, which turns a long answer into an empty one. The endpoint takes no parameters beyond the repo: everything the answer depends on is already on the hub under the caller's own identity, so a client cannot widen it or ask about somebody else's overlap. Where this sits among its neighbours: a merge queue (GitLab merge trains, Graphite) answers the same question AUTHORITATIVELY, BLOCKINGLY and LATE — it needs two finished branches and a CI run — while the workspace-awareness lineage (Palantír, FASTDash, CollabVS, Crystal) answers it EARLY by streaming fine-grained edit events out of every workspace. A ghost check is early like the second and quiet like neither: it streams nothing, computes at two moments a session already talks to the hub, reads only what the hub already holds, and never gates anything. The MODEL half is GATED on the first half finding a candidate and costs at most `GHOST_MAX_FIRES_PER_SESSION` = 1 call: the same detached runner the summarizer and the derived intent use, over the two intent sentences plus the teammate's DECLARED claims from the one overlapping tree — never a transcript, never a prompt, never their machine drafts, because feeding a guess to a model that produces a guess launders provenance one step at a time. What comes back is one sentence naming WHERE the plans collide, or `NONE` (which the prompt states is the usual answer), and it becomes a Tier-1 DRAFT on the READER'S OWN context: `provenance='derived'`, `status='proposed'`, `confidence` fixed at `GHOST_DERIVED_CONFIDENCE` = 0.4 under the 0.5 cap, promotable through the ordinary `review_draft` loop, and RENDERED to nobody else. Rendered, not carried: `services/hints.ts` `listClaimsForContext` selects every non-superseded claim of a context — derived and proposed included — so a ghost draft's BODY rides `GET /api/hints/candidates` exactly as every other claim body of that context does, and what stops another developer's connector showing it as substance is the client-side declared-only gate in `hints/select.ts`. That gate holds, and nothing new is disclosed by it — the teammate's name and their work-context id are already team-visible through presence and the contexts listing — but a ghost draft is a NEW class of body on that wire: text a third party influenced through a model. Narrowing the wire itself is audit row V2-X4, and "rendered to nobody else" is a statement about that client gate, never about the wire. The stored body LEADS with the attribution the connector attaches deterministically and then carries the sentence and the tree (`briefing/ghost.ts` `ghostDraftBody`): the model is shown "SESSION B" and never a name, precisely so it cannot invent anything about a named person, so WHOSE plan the collision is with — and the `get_diagnosis` id that reads their tree — comes from the same row the deterministic half returned. Without it `review_draft` offers a finding about a collision with nobody, with no tree to open and no person to ask. The ORDER is a measurement, not a preference: the one surface a ghost draft is met on is the briefing's own-drafts block, which cuts a body at `MAX_TITLE_CHARS` = 80 while the sentence may be 200, so an appended attribution vanished for every sentence over 73 characters — exactly the case it was added for. It passes the echo-loop exclusion TWICE — once against delivered teammate hints, and once against the very claim bodies and lines it was just shown, which is a guard this surface needs and the others do not: without it a verbatim restatement of Ken's declared finding returns as Alice's derived observation under a fresh id, and `review_draft` confirm then republishes it as Alice's own DECLARED claim. That second check is CONTAINMENT rather than an equality hash (`hints/echo.ts` `isRestatementOf`), because the answer arrives REDUCED — its first non-empty line, cut to `GHOST_SENTENCE_MAX_CHARS` = 200 — so a hash over the whole body could never match a parrot of a body longer than that bound or carrying a line break, and both of those are legal bodies a teammate can write on purpose. A PARAPHRASE is still not caught, and the module says so rather than claiming otherwise. The debt shape carries it across the package boundary: `set_intent` and the derived-intent worker record the sentence and set `ghostPending` in session state, and the next UserPromptSubmit claims that flag under the lock and spawns the worker — an MCP call in connector-core cannot reach a Claude-specific worker, and an agent waiting on a tool result must not wait on a model call.

**Ingest gate (server-side):**
- Same context, same entities, cosine > ~0.93 → no new row; bump `dedup_count` + `last_seen` (15 re-observations of one error = one weighted claim, not 15 rows).
- Cross-session near-duplicate → keep both, auto-add `relates_to` edge. **Never auto-merge across authors — provenance is the product.**
- High similarity + opposite status → flag as **contradiction candidate** for briefings (the deterministic version of "diagnostic conflict detection").
- Secret-scan (gitleaks-style patterns) on all bodies **locally before upload**; schema-reject malformed records.
- **Echo-loop exclusion** (judge-found, mandatory): content injected as teammate hints is marked and excluded from summarizer capture, so Robin's hypothesis can never be re-captured as Nick's independent observation.

Raw transcripts and full diffs never auto-upload. Artifacts (logs, stack traces, diff summaries) default to `needs_approval` — owner-only until released via CLI/elicitation.

## 4. Injection pipeline (knowledge IN)

Principle: **pointers proactive, substance pulled, negatives privileged.** Anchoring a healthy agent on a teammate's wrong hypothesis is worse than silence.

- **SessionStart briefing** (`additionalContext`, ≤600 tokens): active teammates on this repo, top related work contexts (entity overlap ≻ error-fingerprint match ≻ hybrid FTS+vector RRF), open contradictions in this area, recently landed outcomes.
- **UserPromptSubmit** (≤1 hint, ≤300 tokens, <800 ms sync budget, fail-open): fast path is entity overlap + FTS; vector results arriving late are delivered next turn via an async hook. Below the precision threshold: **silence**.
- **Anchoring asymmetry**: proactively inject only (a) `rejected_approach` with evidence — negative knowledge cannot anchor a wrong theory, only save a dead end — and (b) `likely_root_cause`/confirmed claims (which require ≥1 evidence link to reach that status). Bare `proposed` hypotheses and Tier-1 drafts appear only as one-line pointers the agent must deliberately pull via `get_diagnosis`.
- **Trust labels on every hint, normative**: author, age, hypothesis status, confidence, provenance (declared/derived), and **commit drift computed against the reader's HEAD** ("based on a commit 14 behind yours"). Phrased as factual statements, never imperatives (matches Claude Code prompt-injection guidance).
- **The session intent on every surface, one spelling**: `intent (derived): «…»` / `intent: «…»` (briefing/intent.ts — the word, the trust label by positive equality on `declared`, the sentence PROSE-sanitized at INTENT_MAX_CHARS = 120 inside the frame; confidence is never printed for an intent). The briefing's "active now" line carries the freshest session's intent after drift, the work-context line gets an indented intent line of its own (one « » pair per line), the pointer/claim hints and the tripwire reason add `Their intent …`, `get_diagnosis` a `Session intent …` line, `search_related_work` an indented second line per hit, `crosscheck status` the same fragment. Intents are indexed in `normalized_doc` like titles, so a prompt that matches only a teammate's intent reaches the FTS tier — and an intent-only context (no claims yet) earns the existing POINTER hint ("same topic, different files"); the asymmetry is untouched because a pointer carries no body. The SENTENCE is proactively injected, and that is deliberate: an intent is title-class metadata — what a session is about — not a claim. It asserts no cause and carries no evidence, so it can anchor no theory; it is never citable as a finding, and the pointer it rides on is still the only route to the substance. Self-exclusion applies to it like everything else: the hub excludes the caller in the candidates query and hints/select.ts states the same rule again for the claimless case. Budget: intent lines cost the briefing what title lines cost; presence renders first, so five teammates with max-width intents crowd the later sections (contexts, contradictions, solved, drafts, absences) in that order — an accepted consequence of the section priority, stated here.
- **Solicited substance — the ONE documented exception to the asymmetry** (roadmap R2). An answer to a question I asked MAY carry its body proactively, even as a bare `proposed` observation with no evidence — but never as a `derived` one. Tier 1's rule that a draft is pointer-only (§3) is the older and stronger rule, and this is the one surface where the two meet: the hub refuses an answer whose claim is not `declared` (`services/questions.ts`), because a Tier-1 draft delivered as substance is exactly what §3 forbids. The asymmetry exists because *unsolicited* substance can anchor a healthy agent on somebody else's wrong theory; an answer was asked for by this session, about a question this session wrote, so the reader already holds the frame it lands in. It is not a wording rule but a structural one: the hub only puts an answer in a reader's list when that reader is the question's AUTHOR **and is reading from the repo the question was asked in** (`services/questions.ts`) — the exception rests on the reader holding the frame the answer lands in, which is false when the frame is a different codebase; a cross-repo answer waits until its asker next works where they asked, and the exception reaches nothing else — the same author's unsolicited claim with the same weak labels still renders as a pointer with no body in it (pinned by `packages/connector-core/test/question-delivery.test.ts`). The answer still carries every trust label an injected claim carries (author, kind, status, confidence, provenance, age), is still PROSE-framed, still spends one of the session's hint slots, and is delivered exactly once — hub-side through `hint_deliveries` across sessions, and through the session seen-set within one. The cross-session half only holds once a `hint_deliveries` row EXISTS, and UserPromptSubmit is the one hook that never flushes the spool, so the answer branch POSTs its delivery record in the same prompt rather than waiting for the next flush (`flows/hint.ts`); if that POST fails the spooled copy closes the window at the next flush, and until then a second live session may repeat the answer once.
- **Questions for you** (roadmap R2): the SessionStart briefing's first block, before presence, bounded TWICE — at `MAX_QUESTION_POINTERS` = 3 items (the hub's per-target open budget, so one teammate can fill it exactly once) and at `MAX_BRIEFING_QUESTION_CHARS` = 700 characters. The second bound is not belt-and-braces: measured on a saturating briefing, three max-length (400-char) question bodies took 2200 characters on their own and erased presence and teammate contexts entirely. Entries are DROPPED whole, never truncated, and the block says how many it is holding back — a cut question cannot be answered, which is the failure this block exists to prevent, while one left for `list_open_questions` can. With the block bounded, a saturated briefing keeps presence and gives up teammate CONTEXTS first, which is the same order the intent lines already push. It shows the question BODY, which is not a breach of the pointer discipline: a question asserts no cause, carries no evidence and is never citable — it is title-class metadata like the session intent — and a pointer reading "Ken asked you something" would be unanswerable, which is the failure mode an asynchronous channel dies of. It renders FIRST because every other section is ambient while a question is addressed and expires: when the briefing is full, the thing somebody is waiting for must not be the thing that gives way. It carries NO delivery record on purpose — a hint is news and must not repeat, a question is a todo and must repeat until it is answered or expires.
- **Solved before** (VISION.md §1): the briefing's `Previously solved` section and, at the moment a tool fails, one hint of its own. Three tiers feed it, and what a match is allowed to SAY depends on which one found it. A shared **error fingerprint** is content identity — the same failure, byte for byte after normalization — and a tree reached that way may carry its recorded root cause as substance. A shared **file** (same repo) and a **session-intent** overlap say only that two pieces of work are near each other, so they stay pointers. This is a NARROWING of the existing evidence exception rather than a new one: §4's rule already lets an evidence-backed `likely_root_cause` be injected, and this adds a second condition on the surface where the claim's RELEVANCE is itself a guess. Evidence makes a claim trustworthy; content identity makes it relevant; asserting one unasked needs both. The hub sends `rootCause` only for the fingerprint tier and the renderer requires the same kind again before printing it, so a newer or hostile hub buys no substance (`briefing/render.ts` `SUBSTANCE_MATCH_KIND`). The failure-time hint requires that kind for its HEADER too, not only for the body: its sentence asserts content identity ("the same error fingerprint as a diagnosis that was solved"), so a row of any weaker kind would put a false claim above a line that contradicts it. That is the ordinary upgrade order rather than an attack — a hub too old to know `?fingerprint=` ignores the parameter and answers the shared-target listing on the same route — so both the flow (`flows/solved-hint.ts`) and the renderer (`hints/render.ts`) require it, and against such a hub the probe costs one wasted round trip and stays silent. The cause is its own indented line — one « » pair per line — bounded at `SOLVED_ROOT_CAUSE_MAX_CHARS` = 200, and an entry is dropped WHOLE rather than truncated, because a cause cut in half is a different sentence. **It carries its trust labels like every other injected claim**: `root cause · confidence 0.05 · provenance declared: «…»`. The solved predicate gates on status, provenance, evidence and disputes and has NO floor on certainty — `publish_claim` takes the number from the model, so a hedge ("probably X, but I never confirmed it") at confidence 0.05 with one evidence ref is a legal `likely_root_cause` and makes its tree solved on every surface. Relevance is already an inference here; presenting a guess unlabelled as the settled answer would anchor exactly what §4 exists to prevent, and the confidence is the one label that varies. A body arriving without it — a hub older than the field — loses the cause line and keeps the pointer, because substance without its labels is not something the renderer vouches for. The cause is SPAN-redacted rather than whole-body blanked (`spanRedactedUntrusted`, the second surface to opt in after the hub refusal): four of the sanitizer's nine phrase branches are everyday English inside a real diagnosis — `override`, `you must`, `disregard`, `act as` — and blanking the sentence would replace the one thing this feature exists to deliver with a message about a title the reader never saw. Telling the AUTHOR their body would render redacted is the other half of audit row M14 and is not done here.
- **The failure moment is a delivery moment** (VISION.md §1). SessionStart is assembled before the session has failed at anything, so the strongest signal this product has does not exist yet at that point; it appears when a tool fails, and on a long agent turn the next SessionStart can be an hour of re-deriving an answer the team already owns. Claude Code routes failures to `PostToolUseFailure` (`PostToolUse` fires only on success), which is why the connector registers it — SYNC, because it returns `additionalContext`, on the same keystroke-grade 800 ms budget as UserPromptSubmit, measured through the real binary in `test/hint-hook-latency.test.ts`. The fingerprint is spooled BEFORE the probe, so a slow hub costs the hint and never the capture. An ABORT is not a failure and is captured on neither path: `is_interrupt` drops it here, and — because the reference is explicit that cancelling a RUNNING tool fires no failure event at all, its interruption arriving as a tool RESULT — the `interrupted` marker drops it on `PostToolUse`, where `isFailureResponse` reads it. Text every session produces has no business in the one index this product treats as content identity across repos. Only the fingerprint goes on the wire — never the failure text, which `fingerprint()` has already refused to hash if it contained a secret. It spends the ORDINARY hint budget through the same locked check-and-set as the prompt path (`hints/delivery.ts`), so a retry loop cannot produce a stream of these, two hooks racing one failure produce at most one, and a tree the briefing already pointed at stays silent. The same is true of the CALLS and not only of the lines: one fingerprint is probed once per session (`probedFingerprints`, claimed under the state lock before the request), because the hint cap only moves when something was delivered and a retry loop delivers nothing. Counted, never PASS-only: `solved-tree pointers: N shown, M opened in the last 30 days` on `status`, and `doctor` WARNs once `DOCTOR_SOLVED_SHOWN_WARN` = 3 have been shown and none was ever opened — which is what this surface looks like when its matches are wrong. The WARN ends with the call that settles the question (`get_diagnosis <id>`), like `questionWarning`: a warning with no next action gets skipped, and a counter nobody acts on is PASS-only again. The LABEL is `solved-tree pointers` and not this feature's name, because `hint_deliveries` has no source column: the rows are every delivered `work_context` pointer whose tree is solved today, which includes ordinary teammate pointers, so naming the line after the solved matcher would make `doctor` blame it for another surface's precision. Adding that column is the honest fix and a schema change.
- **Ghost checks are pointers and never block** (VISION.md §3). Delivered at two moments: `set_intent`'s own answer, because declaring the plan is the first instant it can be compared with anybody else's, and the SessionStart briefing, in a block placed AFTER presence and BEFORE the ambient teammate contexts — presence orients, a ghost line is the one teammate who is in your way, and the generic context list is the ambient version of the same information, so when the briefing is full the ambient list gives way first. Bounded at `MAX_GHOST_POINTERS` = 2, the solved pointers' ceiling, with the stronger reason that a collision notice is something the reader is expected to ACT on: one or two names is a decision, three is a list to skim. Bounded in CHARACTERS too, at `MAX_BRIEFING_GHOST_CHARS` = 800, because the item bound alone is not a bound: two rows with every field at its cap compose 983 characters under a 114-character header — half of `MAX_BRIEFING_CHARS` for two pointer lines — and the five sections below give way whole to pay for it. Rows are dropped WHOLE and counted by the section's own "+N more not shown", never truncated, because a cut ghost line loses the `get_diagnosis` id that is its entire next action. It is larger than the questions block's 700 for one fewer item on purpose: a ghost line carries up to three of the READER'S OWN paths, which no question line carries, and there is no `list_open_ghost_checks` to read a dropped row from. Bounded per PERSON before it is bounded per line — `GHOST_MAX_FINDINGS_PER_DEVELOPER` = 1, applied after the ranking so each developer keeps their strongest context — because a teammate running three worktrees would otherwise hold the whole block and the second teammate, who is in the reader's way for a different reason, would never reach the wire. `doctor`'s `plan overlap` line counts distinct developers for the same reason. The line states arithmetic and nothing else — this many of YOUR OWN values also sit on somebody else's live context, this many words of YOUR OWN intent appear in their doc, plus their intent (or their title) as the one framed value and `get_diagnosis <id>` as the next action. Both counts are PRINTED ("shares src/a.ts, src/b.ts", "3 words of your intent"), never summarised as "same topic": the intent tier is the one with no target evidence behind it, so an unfalsifiable clause there would be the weakest tier making the least checkable claim. The teammate's plan is rendered next to the TEAMMATE — the `intent: «…»` spelling is possessive-free by design, so position is what binds it to a person, and after a clause containing the words "your intent" it read as the reader's own sentence echoed back. It asserts no cause, quotes no claim body and asks for no decision, so the anchoring asymmetry is untouched and it is NOT a permission gate: the header says "nothing here blocks you" out loud, and the escalation ladder for a hard stop is still the PreToolUse tripwire alone. The header names BOTH next actions in the questions block's shape — "Teammates working where you are (get_diagnosis reads their tree, ask_teammate asks them; nothing here blocks you)" — because a collision is something the reader is expected to act on and reading a tree is only half of that. It claims no TENSE its own lines cannot keep either: the window is `GHOST_ACTIVE_WINDOW_DAYS` = 7, so "right now" sat above lines reading "last active 6d ago", and a header a reader catches overstating is a block a reader stops reading (§10 risk 8). **It discloses nothing new**: the shared values on the wire are the INTERSECTION with the reader's own targets, so every path it names is one the reader's own session already captured, and a shared error fingerprint is reported as a fact ("hit the same failure") rather than as 39 characters of sha256 nobody can read. It is presence-class information — a named teammate is working here NOW — so presence opt-out hides it exactly as it hides the tripwire, and a muted teammate never appears. Counted, never PASS-only: `ghost checks: N overlap notices shown · M checks (K skipped, nobody to compare; …)` on `status`, a `ghost checks` doctor line that WARNs on any booked failure and on `DOCTOR_GHOST_SILENT_FIRES_WARN` = 2 fires that answered nothing, and a `plan overlap` line for the hub half. The skipped count is its own number rather than a fire that landed nothing, because a team with nobody to compare against is this feature working as designed and must never read as a dead runner — and so is `noHubAnswer`, the check that never got an answer OUT OF THE HUB: a connector rolled out ahead of its hub, or a developer on a plane, is a healthy machine, and booking that as a model-layer failure made `doctor` WARN that the local runner was broken one line above the `plan overlap` PASS describing the same condition. The `plan overlap` line owns that condition and reads it in FOUR ways rather than one, because "the hub did not answer" hides the only outcome worth acting on: a 404 is a hub that predates the route, a network failure is a machine that cannot reach any hub and belongs to the connectivity checks, and an answer that does not parse is a hub whose shape this connector does not know — all three PASS with the reason named. An ERROR STATUS other than 404 is the fourth: the endpoint EXISTS and is FAILING (a query throwing on a missing index, a migration that did not run), which WARNs and names the status, because nothing else on a doctor run would say so and fail-open must never mean silently dead (§10 risk 5).

- **Sanitization at render time** (judge-found, mandatory): claim bodies are teammate-authored/LLM-derived text and therefore untrusted input in the reader's context — length-cap, strip imperative/injection patterns, render inside a clearly delimited quote frame.
- **Self-session exclusion + hot-file denylist** (judge-found): a developer's own parallel sessions/worktrees never trigger their presence hints or tripwires; lockfiles, generated clients, and schema files are denylisted/down-weighted for overlap detection.
- **Statusline** = human-facing presence ("Robin → handler.ts · debugging active-seat column") **plus a `last sync 2m ago` health indicator** — fail-open must never mean silently dead.
- **PreToolUse tripwire** (v0.5): file+symbol overlap with an *active* teammate session → `permissionDecision: "ask"` with reason. Escalation ladder: silence → notice → ask. Never hard-deny.
- **Telemetry from day one**: `hint_deliveries` records every injected hint; a subsequent `get_diagnosis` pull marks it useful. This is the measurable precision loop that tunes thresholds — plus a pre-launch golden-fixture corpus, because a 2-dev team will not generate tuning volume for months.

## 5. Data model

Postgres (PGlite or real), Drizzle as the single migration authority. Append-only where knowledge lives.

- `developers` (id, name, email, api_key_hash)
- `agent_sessions` (developer, agent_kind, repo, branch, base_commit, status: analyzing|planning|implementing|testing|blocked|done, last_heartbeat_at) — presence = heartbeat < 90 s, TTL by query; closed sessions reject late writes (idempotency keys on spool replay)
- `work_contexts` (session, title, intent jsonb, status, normalized_doc, tsv generated, embedding vector(768) nullable)
- `work_context_targets` (kind: file|symbol|component|error_fingerprint, value) — the deterministic overlap index. `(kind, value)` is indexed, which is what makes both the derived-contradiction join and the failure-time fingerprint probe one lookup rather than a scan. The solved-match LISTING joins this table to itself, so it is bounded on both sides before they meet — the candidate side must already carry a claim that could make it solved, the live side is the repo's most recently active contexts capped at `SOLVED_MATCH_MAX_LIVE_CONTEXTS` — because a pair-per-shared-value join is quadratic in the traffic of one busy repo: measured at 1.2 s on a 10⁴-context hub with 2000 contexts sharing one fingerprint, and returning nothing, since the unsolved crowd filled the window ahead of the one tree that held the answer. `claims` gained `(work_context_id, created_at DESC)` for the same reason: three hot readers ask "the claims of THESE contexts, newest first" — the solved probe, the solved root-cause body the briefing renders, and `normalized-doc`'s refresh inside every ingest transaction — and `work_context_id` is a foreign key with no index of its own.
- `claims` (work_context, author_session, kind: observation|hypothesis|evidence|root_cause|decision|rejected_approach, body ≤400 chars, status: proposed|partially_confirmed|likely_root_cause|rejected|superseded, confidence, capture_mode: auto|agent|human, provenance: declared|derived, dedup_count, last_seen_at, stale_at, tsv, embedding) — append-only; revision = new claim + `supersedes` edge. A claim's evidenceRefs persist as jsonb on the claim row; materializing them into `supports` edges is a follow-up because referenced claims may arrive later in the same spool flush. v0 ingest dedup is deterministic — same author, same work context, same kind, normalized-body equality — with similarity dedup and contradiction candidates landing with the search block.
- `claim_edges` (from, to, kind: supports|contradicts|deeper_cause_of|supersedes|relates_to, author, note) — recursive CTE walks root-cause chains; no graph DB. `supersedes` is same-author revision semantics; cross-author disagreement uses `contradicts`/`deeper_cause_of`.
- `artifacts` (claim, kind: log|stack_trace|diff_summary, content, sensitivity: team_visible|needs_approval, approved_by)
- `events` (bigserial, kind, payload) — outbox; SSE replays by cursor
- `hint_deliveries` (session, claim/work_context, delivered_at, pulled_at) — dedup + precision telemetry. Read back as the solved surface's own score (`services/solved-counts.ts`): among this developer's recent `work_context` deliveries on this repo, how many pointed at a tree that is solved TODAY (resolved through the one solved predicate, never stored on the delivery) and how many were pulled. Bounded by a window and a row cap, so the numbers are a floor and every surface that prints them names the window. Indexes: `(ref_id, session_id)` for the cross-session "already delivered" probe and `(session_id, delivered_at DESC)` for this counter — `session_id` is a foreign key, which Postgres does not index on its own, so without it `crosscheck status` and `doctor` each scanned every delivery on the hub.
- `questions` (repo, author developer+session, target_developer_id?, work_context_id?, body ≤400, status: open|answered|expired|withdrawn, created_at, expires_at) — the asynchronous question channel (roadmap R2). At least one addressee is a CHECK constraint, not a convention: "never a broadcast" is the property that keeps this from becoming notification spam. `status`, `expires_at` AND `created_at` are hub-owned and ignored on ingest. The third is the one that is easy to miss: `expires_at` is DERIVED from `created_at`, and the two open budgets, the 24-hour rate probe and the dedup scan all read it — so a client that owned `created_at` owned the TTL and all three budgets at once. A question dated 2099 never expires and sorts above every honest one; one backdated past the TTL is invisible to all three and 60 of 60 were accepted. It costs an offline spool replay nothing that matters: the TTL then runs from the moment the hub could first show the question to anybody. The TTL (`QUESTION_TTL_DAYS` = 14) is applied LAZILY on read: every listing carries `expires_at > now()` in SQL, so no cron is needed and a briefing cannot be haunted, while an author-scoped opportunistic flip keeps the "expired unanswered" counter honest. Indexes: `(target_developer_id, repo, status, created_at DESC)`, `(work_context_id)`, `(author_developer_id, created_at DESC)` — `repo` sits INSIDE the inbox index rather than filtering after it, because one person can be the addressee of many questions across many repos. The counters `status` and `doctor` print come from SQL aggregates over that same predicate, never from the bounded listing: derived from a newest-first page, the count stops at the listing bound and the OLDEST question — the one the WARN exists for — is the first row dropped. Both halves of that sentence are scoped to the same repo, and the expired half is windowed to one further TTL, because nothing can clear an expired row and an unwindowed count makes `doctor` exit 1 for ever over one question from last spring.
- `question_answers` (question, claim, answerer, created_at) — the `answers` edge, as its own table rather than a `claim_edges.kind`: `claim_edges.to_claim_id` is a foreign key into `claims` and an answers edge would have to point it at a question id. The claim and the edge are written in ONE transaction. The first answer flips the question to `answered`; later answers still attach, because the later one is often the correction.

Wire format discipline (protocol-first pass, internal for now): every record in a versioned envelope `{cx: "0.1", id, ts, producer, kind, body}`; consumers must ignore unknown fields and kinds. Published as zod schemas in `packages/schema` from day one so the protocol is *extractable* later — but **no frozen public spec and no conformance suite until a second adapter exists** (both judges: premature standardization is the protocol-first trap; LSP won because VS Code shipped, not because the spec existed).

Staleness model: heartbeat TTL kills ghost presence; time-decay ranking (half-life ~14 days); merged-branch detection (base_commit reachable from main ⇒ context marked *landed*); claims marked stale when their referenced files change on main afterward; commit drift shown on every hint. Nothing is deleted — rejected and stale claims remain queryable history (the long-term team-memory byproduct) but stop being hints. Retention/compaction policy is an open item before public launch.

## 6. Semantic search

Hybrid from day one, but with honest degradation:
- Exact matching on files, symbols, error fingerprints (no embeddings needed — highest precision).
- Postgres FTS (`websearch_to_tsquery`) over the **normalized doc** (title + symptom phrases + components + hypothesis summaries — never raw transcript).
- Optional vector layer, RRF-fused: OpenAI `text-embedding-3-small` truncated to 768d (hosted default) or Ollama `nomic-embed-text` (local default), pluggable; model change = re-embed migration. **With no key configured, matching degrades to FTS + exact targets and still works** — no mandatory external dependency in the default install.
- **WHO and WHEN, not only WHAT** (roadmap R1): `search_related_work` takes `developer` (full name or any email the hub knows them by, resolved hub-side through the same `resolveDeveloperRef` the mute surfaces use) and `since` (`14d`, `72h`, or an ISO date; at most 365 days, refused rather than clamped, because a silently narrowed window answers a different question with nothing saying so). Both are applied INSIDE every tier's `WHERE` — each tier list is bounded at `TIER_CANDIDATES`, so a filter applied after the bound deletes the wanted row instead of finding it — and ranking, RRF and decay are untouched. `since` filters on ACTIVITY, `coalesce(updated_at, created_at)`: the timestamp every surface already renders as a row's age and the input to time decay, so a hit inside a 14-day window can never print "40d ago". That timestamp moves when the work context ITSELF changes (title, description, intent, status) and not when a claim is filed into it, so a long-running context whose only fresh activity is claims falls outside a tight window — a deliberate false negative, because admitting it while the same answer printed its stale age and decayed it as 40 days old would be the dishonest half of the trade. Widening a context's activity to include its claims is one edit to the row's timestamp, not to the filter, and it moves ranking and every rendered age with it. Indexes behind the filters: `agent_sessions (developer_id, repo)` and `work_contexts (coalesce(updated_at, created_at) DESC)`.
- **A filter that does not resolve is an ERROR, never an empty result.** "No work context matched" in answer to `developer: "Kenn"` reads as "Ken has done nothing", and an agent acts on that by redoing Ken's work — so an unknown name comes back naming the closest known spellings, and an ambiguous one naming the candidate addresses (each bounded to fit `MAX_HUB_MESSAGE_CHARS`, which is what the connector quotes them into). When a filter DID run, the answer names it (`Filters: Ken · active in the last 14d`, and `Filters: Ken · ken.ohara@example.com · active in the last 14d` when the hub reports that display name is shared, so a caller who was refused once and retyped an exact address does not read a header that has thrown that distinction away again), and an empty filtered result says out loud that the filters are part of that answer. Search does not self-exclude — hiding your own tree would make `get_diagnosis` on it unreachable — so `developer: <myself>` is a legitimate call and renders `Ken (you)` so the results cannot be mistaken for a teammate's; where self-exclusion DOES apply (the hints candidates query), the developer filter intersects with it and never lifts it.

## 9. Non-goals (v1)

- Automatic semantic/architectural conflict **inference** — deterministic overlap + explicit `contradicts` edges + contradiction candidates deliver most of the value; inference is a research project (tempo-agents died trying).
- Agent-to-agent CHAT — wrong topology; payloads stay A2A-extension-shaped for later. Roadmap R2 does not reopen this: a question is a RECORD that waits, not a channel. Nobody is online at the same time, there is no session, no turn-taking and no delivery guarantee — it reaches its target at their next SessionStart, is answered by an ordinary claim, and expires if nobody answers. A live agent-to-agent channel would still be theatre, because the teammate's agent is not running when you ask.
- Transcript-tailing daemon — Stop-hook capture dominates; raw-transcript privacy blast radius not worth crash-capture.
- General team memory as headline; Redis/queues/WebSockets/graph DB; multi-team tenancy, SSO, per-repo ACLs; auto-merged "team truth" across authors; shared cloud workspaces; hosted SaaS.

## 10. Top risks

1. **Noise → trust collapse → uninstall.** Hard budgets (1 hint/prompt, 5/session), silence-when-unsure, negatives-first, seen-set dedup, telemetry-tuned thresholds, per-dev mute, ask-never-deny. The failure-time solved hint (VISION.md §1) is the first surface that fires where NOBODY IS TYPING — inside an agent turn, on a retry loop that can run dozens of times a minute — so it takes no new allowance: it spends the same five-per-session budget through the same locked check-and-set, and treats the briefing's own solved pointers as already seen. The cap alone does not bound the CALLS, and an earlier version of this line said it did: the counter moves only when a hint was delivered, so on the two common paths — the hub holds nothing, or it holds a tree already shown — the cap is never reached and every repeat of one failure bought another round trip inside the agent's turn (measured: 40 identical failures, 40 probes of one fingerprint; 10 against a hub that never answered, 4475 ms). So a fingerprint is asked about ONCE per session, claimed under the state lock before the call (`probedFingerprints`); the cost is that an answer appearing mid-session waits for the next one. The precision counters exist for the same reason: a surface that asserts relevance unasked must be able to be caught being wrong, and "shown repeatedly, opened never" is what that looks like.
2. **Cross-user prompt injection via the claim store.** Claim bodies are untrusted input: sanitize + length-cap at render, quote-frame, factual-statement wrapper; never render imperatives.
3. **Privacy.** Summarization and entity extraction run locally; only structured claims + hashed fingerprints + paths upload; secret-scan before POST; artifacts owner-gated; per-dev revocable keys; fully self-hosted. Presence is also a surveillance surface — per-dev visibility opt-out is a v0.5 requirement, not an afterthought (EU works-council reality). **Teammate email addresses are disclosed to a caller in exactly two places, both deliberate and both minimal** (roadmap R1): the ambiguity refusal, which lists the addresses of the same-named developers because the address is the only thing that tells two people called Ken apart and is therefore precisely what the caller must retype; and the applied-filter line, which carries the resolved developer's address ONLY when their display name is shared, so an answer never republishes an address nobody needed. Defensible because these are the git author addresses any teammate can already read in `git log`, and bounded because nothing else on this hub lists the team: there is no "who works here" endpoint, the ambiguity list is capped in characters, and the unknown-name refusal offers NAMES rather than addresses. A future surface that wants to widen this — a directory, a picker, question targeting — is adding a new disclosure and owes its own line here. **Question targeting (roadmap R2) is the first surface to arrive under that rule, and it widens nothing**: `ask_teammate` resolves its target through the SAME `lookUpDeveloper` and answers an ambiguous name with the SAME `describeAmbiguousDeveloper` sentence search does, so the addresses it can disclose are exactly the ones search could already disclose, to exactly the same caller, under the same character bound. It adds no listing of its own — a caller cannot enumerate the team by asking questions, because a name that resolves discloses nothing and a name that does not resolve returns the same three closest NAMES search returns. The two mute routes were moved onto those sentences in the same change, so the disclosure now has one implementation rather than three.
4. **Capture quality.** Tier ladder, derived-confidence cap 0.5, ingest validation + dedup, promotion loop, golden-transcript CI fixtures.
5. **Silent death.** Fail-open everywhere + a sleeping-laptop host means hints can stop invisibly: statusline last-sync indicator + `crosscheck doctor` (verifies hook contract against the installed Claude Code version + hub liveness) are v0 features.
6. **Staleness/drift.** TTL presence, decay, landed detection, commit drift vs the reader's HEAD — including the inverse case where the teammate's fix already reached your branch via rebase.
7. **Summarizer cost on the dev's own quota.** Gating, debounce, per-session caps, and a visible per-day token estimate.
8. **Prediction theatre** (VISION.md §3). A collision warning that fires on ordinary co-location is worse than no warning: people learn to skip the block, and the one real conflict goes with it. Every prior-art system with published numbers spends its design on exactly this — ConE's 71.5 % usefulness rate rests on its exclusions, not on its detector — so the ghost check is a COUNT rule a reader can check against the line they were shown ("two of your files", "hit the same failure", "three words of your intent") and never a score, and it drops hot values and sweeps before it counts anything. The model half is GATED on the deterministic half, so a quiet repo costs no tokens; what it produces is a draft its own author reviews, not a warning a teammate is shown; and nothing in it blocks, which is why the header says so. The number that would tell us this is going wrong is the one the solved matcher already has: shown often, acted on never — `ghost checks: N overlap notices shown` on `status`, beside the outcome split. This risk NUMBERING is append-only on purpose: ~20 source comments cite `§10 risk 3` and `§10 risk 7` by number, and renumbering would make every one of them point at the wrong paragraph.
